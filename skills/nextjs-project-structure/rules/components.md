# 组件规则

> 回答一个问题：我写的这个组件该放哪。路由怎么拆见 [项目结构与拆分原理](./architecture.md)，请求和错误边界见 [数据请求与边界](./data-and-boundaries.md)。

## 三层归属

| 层 | 定位与初衷 | 放什么 | 约束 |
| --- | --- | --- | --- |
| `@scopify/ui`（`repo/frontend/packages/ui`） | **最小可复用 Base**：抽象出的最小复用单元，多路由与全局公用的基石，类似 shadcn UI 的可拆解原子层次 | shadcn 原生原子组件，以及抽象出的无业务属性、可自由组合的最小 Base 组件 | 不依赖 store、路由、API、i18n；文案和回调全部通过 props 传入 |
| `components/<领域>/`（Web 应用内） | **基于 Base 改造的领域多路复用组件**：底层 Base 满足不了业务要求时演进而来 | 基于 Base 改造或组合、带业务属性（store、Query、i18n、路由），且被两个及以上路由复用的领域组件；跨页面领域（播放器、歌词、侧栏等） | 按业务领域分目录；`shared/` 只放跨领域的通用业务组件 |
| `<路由>/_components/` | **页面特有组件**：特有的基于 Base 改造但不多路复用的小组件与特殊需求 | 某个页面或 `@slot` 专属的展示区块、骨架屏、表单、视图等；无法直接用 Base 且无多路由复用价值 | 仅服务当前页面，不允许被其他路由导入 |

## 选择顺序

写组件前，按这个顺序往下走，第一个满足的就是答案：

1. **已有 Base 能用 props 和 token 满足吗？**能，就直接用，不复制、不包一层。
2. **Base 满足不了要求，需要改造或新建：**
   - **能抽象为多路由公用的最小可复用案例、无业务耦合吗？**是，作为 Base 放进 `@scopify/ui` 的 `scopify/components/`。
   - **是基于 Base 改造、带有业务耦合（store/API），且被两个及以上路由复用吗？**是，放 `components/<领域>/`。
   - **是当前路由特有的特殊需求、基于 Base 改造但不多路复用吗？**放使用它的路由的 `_components/`。

拿不准时放 `_components/`。需要共用时再升级，不要为了「以后可能复用」预先放进全局。

## 升级规则

`_components/` 里的特有组件被第二个路由需要时，**不要跨目录导入**，把它移走再导入：

- 能够抽象为无业务耦合的最小可复用案例、由 props 驱动 → 升级到 `@scopify/ui` 的 `scopify/components/`（成为 Base）
- 带 store、Query、i18n、路由的业务组件 → 升级到 `components/<领域>/`（基于 Base 改造的多路复用业务组件）

被其他路由导入 `app/` 下的文件是被禁止的。

## `_components/` 规则

- 可以放在路由目录，也可以放在 `@slot` 目录下。Next.js 不会把下划线开头的私有目录当路由。
- 只放该路由专属的、有自己状态或逻辑的区块：区域的展示组件、骨架屏、表单、列表视图。
- **不要拆得太碎。**只被一处使用、几行就能写完的东西（无效 id、空状态、加载中、错误横幅、只包一层的容器、头部背景）直接写在使用它的 `page.tsx` 或 `layout.tsx` 里，不单独建文件；外层容器、栅格、背景这类排版本来就归 `layout.tsx`。判断标准见下面的「拆分的标准」。
- 用 Context 在多个 slot 间共享的状态，Context 和 Provider 写在同一个文件里。
- 在路由里改造现有 Base 组件之前，先确认 props 和 token 真的表达不了；能表达就在调用处用 props。
- 类型、hooks、常量仍然全局，通过 `@/types/...`、`@/hooks/...` 导入，不在 `_components/` 里定义。
- 同一个路由里的组件用相对路径导入（`./_components/Xxx`）。

## `components/` 里怎么组织

- 必须先按业务领域建子目录，禁止把组件平铺在 `components/` 根层。
- 新业务出现时，直接新建 `components/<领域>/`，不要往 `shared/` 里堆。`shared/` 只放跨多个领域的通用业务组件。
- `components/ui/` 是 `@scopify/ui` 之前遗留的基础组件目录。新的通用基础组件放 `@scopify/ui`，不往这里加；改动到这里的组件时顺手评估是否迁到 `@scopify/ui`。

## `@scopify/ui` 怎么用

`@scopify/ui` 有两层，依赖方向是单向的：

```text
Web 业务组件  →  @scopify/ui/scopify  →  @scopify/ui/shadcn
                              └──→  共享主题 token
```

| 层 | 内容 | 能不能改 |
| --- | --- | --- |
| `shadcn/` | shadcn CLI 生成的原生组件，用 `@scopify/ui/shadcn/components/xxx` 导入 | **不能手改**。要升级就通过 shadcn CLI 刷新 |
| `scopify/` | 产品扩展：原生 props 与 token 表达不了的结构或行为，以及抽象出的最小可复用 Base 组件，用 `@scopify/ui/scopify/components/xxx` 导入 | 可以，但不能依赖 store、路由、API、i18n |

规则：

- 标准 props、`className`、组合与共享 token 能满足的，直接用原生组件，不要为了改个 prop 名、套个布局类再包一层。
- 只有改了 DOM 结构、交互或无障碍行为，或者样式无法用 token 表达时，才把原生组件复制到 `scopify/components/` 再扩展。扩展起一个体现产品概念的名字（如 `PlaybackButton`），不要覆盖原生名字（`Button`）。
- 一个无业务逻辑的特有组件只有一个页面在用时，留在那个页面的 `_components/`，第二个页面需要共用且可抽象为最小案例时再升级到 `scopify/`。
- 只改颜色、圆角、间距这类 token 能表达的值，改主题 token，不要复制组件。
- 样式沉淀到共享的 `scopify/theme.css` 必须是多个扩展都需要的产品语义；只有一处用的布局样式留在调用处。

细则见 [ui-package-boundaries](../../ui-package-boundaries/SKILL.md)。

## 拆分的标准

拆分的核心动力是：**内容变多、复杂度上升，且这一块是集中为了表达一个完整、独立的功能**。拆分不是简单的行数切分，也不是一句空泛的“看可读性”，而是为了**职责聚焦与功能表达清晰**。

- **为什么拆分**：当一个文件里逻辑与内容越来越庞大，继续堆积会导致单块理解负担过重；而其中某一部分（例如播放控制、独立的交互表单、一个有自己状态协议的数据区块、一组专属的副作用订阅）是**专门为了表达一个特定功能**时，就应该将其拆分为独立的子组件、hook 或 slot。
- **拆分的标准（满足两者才拆）**：
  1. **内容多、复杂度高**：逻辑或结构达到一定体量，需要通过拆分降低单块心智负担；
  2. **功能独立明确**：拆出来的这一块能起一个精准的名字，全心全意表达这个功能本身，输入输出清晰，读它的人不用时刻联想周围的上下文。
- **什么时候不该拆**：
  - 内容本就不多，几行就能讲清楚的事（如简单的空状态、错误提示、单层容器），拆出去只会让人多翻文件、增加跳转心智负担；
  - 虽然代码长，但从上到下是在线性表达同一件连贯的事；
  - 纯粹为了把大文件削短而机械切开、切开后两边依然高度耦合需要来回对照的代码。
- **自查办法**：
  - 这一块拆出去后，能不能用它的名字准确说出「它实现了什么功能」？
  - 改动这项功能时，是不是只需要看这个拆分出的模块，而不需要同时改动或反复对照原组件的上下文？如果答案是肯定的，这次拆分就是对的。

## 写法

- 一个文件围绕一个主要组件；只服务于它的小辅助组件可以写在同一个文件里，不必为每个都建文件。
- 默认写 Server Component，用到 `useState`、`useEffect`、事件处理、浏览器 API 时才加 `'use client'`，并写在文件第一行。Client 组件尽量下推到叶子节点。
- 组件里一块与渲染无关、自成一件事的逻辑（订阅、同步、一组相关的 `useEffect` 加状态）提成 `hooks/` 里的 hook，名字说清它做什么；被多处复用的逻辑同样提取。一行 `useState` 留在组件里。
- 在写新组件前，先看 shadcn 有没有现成组件，见 [shadcn 组件清单](../assets/shadcn.md)。

## 速查

| 我要写…… | 放哪 |
| --- | --- |
| 一个基础按钮、对话框、输入框等原子 Base | 直接用 `@scopify/ui/shadcn` |
| 可抽象为多页面共用的最小 Base、不碰 store/i18n 的卡片骨架或分页器 | `@scopify/ui` 的 `scopify/components/` |
| Base 满足不了要求，基于 Base 改造且带业务逻辑（store/Query），多个页面复用 | `components/<领域>/` |
| 某个页面特有的特殊需求，基于 Base 改造但不多路复用 | 页面专属的 `_components/`（如 `comment/@header/_components/`） |
| 现有组件差一点，页面里要改 DOM 结构且仅本页面使用 | 复制到该页面的 `_components/` 再改造 |
