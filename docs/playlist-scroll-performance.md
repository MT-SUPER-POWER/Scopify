# 歌单滚动性能采样（2026-09-16）

每日推荐的滚动重复渲染已消除；长歌单节点数量保持有界，但开发环境的大幅滚动仍存在长帧，不能据此宣称整体 CPU 问题全部解决。

## 采样方法与边界

- 在用户前台 Chrome 的 `127.0.0.1:3000` 页面，通过浏览器工具向下滚动一屏、向上滚动一屏，重复 3 次，共 6 个 scroll 事件。
- 页面临时加入 React Profiler、MutationObserver、requestAnimationFrame 和 PerformanceObserver；最后一次滚动后继续记录 1.8 秒。结束后已移除全部临时探针。
- 环境是 Next.js 开发服务器，存在 React DevTools 扩展。帧数据包含滚动后的空闲窗口，不能换算成持续滚动 FPS、CPU 百分比或生产环境性能。
- DOM 数量为当前文档中的 Element 数量，不等同于 DevTools 的全部 DOM nodes（后者还包括文本、脱离文档的节点等）。
- 首次加载、热更新、后台限速、用户切换歌单的记录不作为有效对比。

## 已实施

1. 滚动开始/结束保持同一歌曲行组件层级，不切换右键菜单包装。
2. 80 首以内使用原生滚动，避免小列表频繁维护虚拟窗口；更长列表继续虚拟化。
3. 稳定排序数据、歌曲 key、节点 ref、播放回调、拖拽属性和样式引用。
4. 将歌曲内容拆为 memo 组件，隔离 Radix/dnd-kit 事件属性变化引起的重复内容渲染。
5. 右键菜单的查询、状态订阅和动作逻辑在打开时初始化，关闭后释放；建单弹窗打开期间保留动作组件。
6. 虚拟列表按实际 62 px 行高估算，取消滚动回调中强制同步 React 提交。
7. 移除建单弹窗重复且直接渲染在 tbody 下的遮罩，复用 Content 内的 Portal 遮罩。

## 空载周期任务补充（2026-09-16）

继续采样发现，暂停且不滚动时，`PlaybackAuthority.publishClockAnchor()` 每秒发布的心跳会进入 `PlaybackProjectionProvider`。Replica 返回内容相同的新对象，Provider 无条件替换缓存并通知 `useSyncExternalStore`，使主界面订阅者每秒重复渲染。

- 修正前的一个 5 秒前台窗口：指针事件 0，6 次 React commit、累计约 364 ms 渲染；5 个长任务约 102 / 74 / 80 / 98 / 65 ms，均可归因到播放时钟定时器。其他静置窗口同样出现每秒一次的长任务。
- 修正后：对投影快照做浅比较，字段未变化时保持快照引用并跳过界面通知；仍接收心跳，保留连接看门狗和真实状态变化通知。
- 首页连续 3 个约 5 秒的前台窗口无超过 50 ms 的长任务，React 渲染累计分别约 38 / 49 / 0 ms。窗口记录到 2 / 2 / 3 次指针事件，因此不冒充完全无交互样本。每日推荐页最终两个约 5 秒的静置窗口均为 0 次指针事件、0 个长任务，React 渲染累计分别为 0 / 1 ms（UTC 03:37:27、03:37:32）。
- 用户已自行确认移动鼠标引起的 CPU 升高与 Chrome 调试环境有关，本轮不再针对鼠标路径修改业务代码。
- 新增实际 Replica → external store 回归测试：暂停心跳不换快照、不通知界面；播放、定位、喜欢和音量变化仍更新；停止收到心跳后看门狗仍报告断连。修正前首项失败，修正后 3 项通过。

这是主线程长任务与 React 渲染的对比，没有直接读取 CPU 百分比。开发工具和页面初次加载的开销未包括在修复结论中。
